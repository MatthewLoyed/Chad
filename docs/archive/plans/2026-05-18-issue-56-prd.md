# Product Requirements Document (PRD)
## Issue #56: Model Dropdown Selection Global Model Alignment

## Problem Statement

When a user changes the model selection dropdown in the desktop UI (e.g., switching to Claude 3.5 Sonnet or activating a Local Model), they expect that selected model to power all of their interactive turns. Currently, if a user starts an interactive turn that is classified as an `agent` harness (requiring system tools or multi-step reasoning), the system ignores the selected model and falls back to the default Gemini 2.0 model defined in `config.yaml`. This results in highly confusing behavior where the dropdown only works for simple conversational turns, but silently resets for coding and workspace exploration tasks.

## Solution

Ensure that whichever model is selected in the UI dropdown is used globally as the underlying LLM for all user-interactive harnesses (`conversation`, `text`, and `agent`). Changing the harness (e.g., executing a standard chat conversational loop versus a tool-using agentic loop) should change the runtime environment, but NOT change the active LLM.

## User Stories

1. As an assistant user, I want the model dropdown selection to globally dictate the active LLM for all my queries, so that I have consistent control over which model I am chatting with.
2. As an assistant user, I want to switch to a local model (via LM Studio or Ollama) and have it execute both conversational chat and tool-calling agent tasks without the system silently reverting to cloud defaults.
3. As an assistant user, I want my cloud model override (e.g., Claude 3.5 Sonnet) to persist even when I ask the assistant to search the workspace or view local files, so that I can utilize different advanced models for agentic tasks.
4. As an assistant developer, I want the internal routing logic to preserve fast/cheap defaults for purely administrative and classification tasks (like the initial routing classifier) while ensuring the main user-interactive loops use the user's selected model.

## Implementation Decisions

### Modules to Modify
- **`src/core/intelligence/model_router.py`**:
  - Update `ModelRouter._ensure_model` Step 1 (Local Model Override) to whitelist `'agent'` in addition to `'conversation'` and `'text'`.
  - Update `ModelRouter._ensure_model` Step 2 (Global Cloud Override) to whitelist `'agent'` in addition to `'conversation'` and `'text'`.

### Architectural Rules
- The dropdown selection in the UI will configure the active **LLM** globally.
- The active **LLM** is loaded into the active **Harness** (such as `conversation`, `text`, or `agent`) for all user-interactive turns.
- We do not route different LLMs based on category or intent; we simply run the selected LLM inside the chosen Harness.

## Testing Decisions

- A good test must verify external routing behavior by simulating different dropdown configurations (local model active, cloud override active) and calling `route` or `get_model_for_category` on the router.
- We will create a new unit test suite: `tests/unit/test_model_router.py` to assert:
  - Global cloud model override works for `'agent'`, `'conversation'`, and `'text'` categories.
  - Local model override works for `'agent'`, `'conversation'`, and `'text'` categories.
  - Non-interactive categories (like background workers or routing classifiers) are not overridden by the dropdown selection.
- We will use existing tests in `tests/` as prior art for unit testing patterns.

## Out of Scope

- Dynamically hot-swapping models mid-agent turn (once a LangGraph execution starts, the LLM is locked for the duration of that turn).
- Hot-swapping the small intent routing classifier model (this remains locked to standard low-latency defaults).
